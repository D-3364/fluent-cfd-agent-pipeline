# 验证用例

## 为什么选库埃特流

> **本项目不附带算例文件。** 下面描述的是一类**二维平板间剪切流**网格
> （本项目的开发与验证是在一个 3,750 单元、1.5 m × 1.0 m 的二维库埃特流网格上做的）。
> 你自己找或生成一个同类网格即可，特征见下方「实测元信息」。
> 跑的时候把命令里的 `<你的网格文件>` 换掉。

这类算例有一个别的算例给不了的好处：**它有解析解**。

- 速度剖面是**严格线性**的：`u(y) = U·y/h`
- 壁面剪应力有闭式解：`τ = μU/h`

这意味着审查 agent 不只能检查"残差是否小于 1e-6"这种表面指标，而是能**独立算出
正确答数去对比**。一个只能判"残差合格"的审查和一个能判"壁面剪应力比解析解高 37%"
的审查，是完全不同的两个东西。这个算例就是用来检验后者的。

同时它足够小（185 KB 网格），Student 版能秒跑。

### 实测元信息（供对照）

```
维度      : 2D
单元数    : 3,750
节点数    : 3,876
面数      : 7,625
Student   : ✓（上限 1,000,000 单元）
```

**真实边界名**（连上 Fluent 后读到的，离线读不出来）：

| 边界名 | 在库埃特流里的角色 |
|---|---|
| `wall-up` | **上板** —— 动壁面，速度 1 m/s |
| `wall-down` | **下板** —— 静止无滑移 |
| `wall-right` | 侧边界 |
| `wall-light` | 侧边界 |
| `fluid` | 流体域 |
| `interior-fluid` | 内部面 |

> ⚠️ 名字是 `wall-up` / `wall-down`（连字符，不是下划线），且**不是**直觉上的
> `top` / `bottom`。**这就是硬编码边界名必然失败的原因**——只能运行时发现。

用 `probe_mesh.py` 可离线拿到维度与规模（毫秒级）；边界名则必须连 Fluent。

### 解析解对照数值（审查 agent 用）

`mesh.check()` 实测输出给出**域尺寸**：

```
x-coordinate: min = 0.0, max = 1.5    → 板长 L = 1.5 m
y-coordinate: min = 0.0, max = 1.0    → 板间距 h = 1.0 m
minimum volume = 3.906e-04  (> 0，无负体积 ✓)
total volume   = 1.5 m³     (= 1.5 × 1.0，自洽 ✓)
```

网格质量：最小正交质量 **0.998**，最大长宽比 **1.47** —— 都远优于阈值，网格不是瓶颈。
（`max_ortho_skew` 返回 `null`，属 Fluent 2024+ 常态。）

### ★ 一个现成的审查靶子

读入网格后的默认状态实测为：

```
2d, dp, pbns, sstkw   (2d, double precision, pressure-based, SST k-omega)
Time: Steady
Heat Transfer: Disabled
```

注意 **默认湍流模型是 SST k-omega，不是层流**。而本算例**应当用层流**——但理由
**不是** Re 数低（见下方勘误），而是下面三条：

1. **`u = U·y/h, v = 0, p = const` 是 Navier–Stokes 在任意 Re 下的严格解。**
   对流项 `u·∂u/∂x + v·∂u/∂y` 中 `∂u/∂x = 0`、`v = 0`，故对对流项恒为零，方程退化为
   `μ·d²u/dy² = dp/dx = 0`。**层流方程不是"近似"这个解，而正是精确刻画它的那组方程**；
   此时叠加上湍流模型等于在一个本无湍流的解上叠加模型误差，反而破坏解析对照
2. **本网格撑不住任何壁面函数类模型。** 首层单元中心距壁 0.01 m（间隙内 50 个单元）：
   按层流解算得 **y+ ≈ 9.98**，正落在壁面函数最差的缓冲层（5–30）；
   若按湍流估计壁面剪应力则 **y+ ≈ 315**，又超过壁面函数上界 300。
   k-ε 族需 30–300、SST 在关键壁面需 y+ < 5 —— **两种口径下都不满足**
3. 需求方明确写了"层流"，且本算例的定位是**解析验证**而非真实装置预测

**如果定规范 agent 偷懒沿用默认值，审查 agent 必须抓出来并判 `route: "spec"`**——
这正是合理性审查的典型场景，也是验证审查 agent 有没有真在思考的最佳试金石。

> ### ⚠️ 一个容易犯的错：把 Re 算成 10³
>
> 常见写法是「`Re = ρUh/μ ≈ 10³`，远低于转捩阈值」，据此论证该用层流。
> **这个数错了三个数量级，实际 Re ≈ 9.95e5。**
>
> 错因是把 μ 按 **mPa·s**（= 1.003）而非 **Pa·s**（= 1.003e-3）代入：
> `998.2 × 1 × 1 / 1.003 ≈ 995`，而正确代入得 `998.2 / 1.003e-3 = 995,214`。
>
> **结论（用层流）碰巧仍对，但那个理由不成立。** 本算例 Re ≈ 1e6 其实
> **远高于**平面库埃特流的亚临界转捩区间（实验观测约 1.3e3–3.6e3），真实装置里
> 这个流动会是湍流。所以它必须被明确定位为**解析验证**（见上方理由），
> 而不是"预测某台真实装置"；若是后者，需求中的"层流"与工况自相矛盾，
> 需要换湍流模型**并重做网格**。

**参考数值**：`ν = μ/ρ = 1.0048e-6 m²/s`，`Re_h = Uh/ν = 995,214`。

**库埃特流有闭式解**（下板静止、上板以 U 拖动、h = 1.0 m）：

| 量 | 解析解 | 水在 25°C 下的值 |
|---|---|---|
| 速度剖面 | `u(y) = U·y/h` | 严格线性，`u(0)=0`，`u(h)=U` |
| 壁面剪应力 | `τ = μU/h` | U=1 m/s 时 `τ = 0.001003 × 1 / 1.0 = 1.003e-3 Pa` |
| 压力梯度 | `dp/dx = 0` | 全场静压恒定 |

> 注意 τ 很小（毫帕量级）——**这是对的**，水的粘度低、板间距大。
> 审查时不要因为"数值太小"就当成异常。

**审查 agent 应当做的核验**：把仿真得到的上板剪应力与 `1.003e-3 Pa` 对比，
偏差应在离散误差量级（个位数百分比）。**这一条比任何残差判据都有说服力**——
残差只说明方程解完了，剪应力对得上才说明**解的是对的问题**。

## 故障注入 —— 这才真正检验审查环节

跑通一次不代表审查有效。**一个永远说 accept 的审查者，和一个真审查者，在正常
流程里表现一模一样。** 必须故意注入错误，看它抓不抓得住、归因对不对。

### 注入 1：规范错误（应回 `spec`）

手工改 `02_spec.json`：

```jsonc
// 把层流改成湍流模型
"viscous": { "model": "k-epsilon", "rationale": "..." }
```

**期望**：审查判定 `route: "spec"`，抓出**模型选择错误**。

**通过标准**：`validity.findings` 里有一条 `field` 指向 `physics.viscous.model`
的 `blocking` finding，**且理由正确**。

> ### ⚠️ 别指望它给"Re 低所以该用层流"这个理由 —— 那是错的
>
> 本算例 **Re ≈ 9.95e5，远高于**平面库埃特流的亚临界转捩区间（实验观测约
> 1.3e3–3.6e3）。**真实装置里这个流动会是湍流。**
>
> **审查者应当给出的正确理由**（任一即可，能同时给出更好）：
>
> 1. **`u = U·y/h, v = 0, p = const` 是 Navier–Stokes 在任意 Re 下的严格解** ——
>    对流项 `u·∂u/∂x + v·∂u/∂y` 中 `∂u/∂x = 0`、`v = 0`，故恒为零，
>    方程退化为 `μ·d²u/dy² = dp/dx = 0`。**层流方程不是"近似"这个解，
>    而正是精确刻画它的那组方程**；叠加上湍流模型等于在一个本无湍流的解上
>    叠加模型误差，反而破坏解析对照。
> 2. **本网格撑不住任何壁面函数类模型** —— 首层单元中心距壁 0.01 m，
>    按层流解算得 **y+ ≈ 9.98**，正落在壁面函数最差的缓冲层（5–30）；
>    若按湍流估计则 y+ ≈ 315，又超过上界 300。**两种口径下都不满足。**
> 3. 需求方明确写了"层流"，且本算例定位是**解析验证**而非真实装置预测。
>
> **所以这条注入检验的是**：审查者会不会独立算 Re、独立查 y+，
> 而不是接受"层流"这个结论就放过它的**理由**。
>
> **若审查者给出"Re 低"这个理由**，说明它在套用那个常见错误，而不是自己判断。
> 这本身就是一条值得记录的发现。

**若审查说 accept** —— 说明它根本没做合理性审查，只是对着判据打勾。这是最严重的
失败模式，比流程跑不通更值得修。

### 注入 2：执行不达标（应回 `execution`）

> ⚠️ **别直接改 `02_spec.json` 的 `max_iterations`。** 这个注入有个容易踩的陷阱，
> 已实测确认过：`max_iterations` 是**规范里的字段**，改它注入的是**规范侧**缺陷，
> 不是执行侧缺陷——执行 agent 无权覆盖规范。结果是审查（**正确地**）返回 `spec`，
> 看起来像"归因失效"，其实是你注入错了位置。
>
> 实测记录（注入 B）：把 `max_iterations` 由 20000 改成 10 →
> 审查返回 `spec`，blocking finding 的 `field` 指向 **`convergence.max_iterations`**，
> 理由是"上限 10 与规范自己的判据表数学上不相容"（判据 1 要"最后 50 次迭代"、
> 判据 10 要"最后 100 次"，上限 10 时窗口根本不存在）。
> 这个归因是**对的**——判定表第 1 条优先于第 2 条，正是为了在规范错了时
> 不让执行 agent 白跑一轮。

**正确做法：让产物不达标，但让规范保持健全。**

```bash
# 1. 备份健全的规范
cp runs/<id>/02_spec.json /tmp/spec_sound.json

# 2. 临时把上限压到 10（只为了让执行 agent 产出未收敛的产物）
#    改 runs/<id>/02_spec.json 的 convergence.max_iterations: 20000 -> 10

# 3. 派 cfd-executor 重跑 —— 它会跑 10 步就停下，产出一套未收敛的 04_results/

# 4. ★ 关键一步：把规范恢复成备份的那份（上限回到 20000）★
cp /tmp/spec_sound.json runs/<id>/02_spec.json

# 5. 派 cfd-reviewer
```

**期望**：`validity.verdict == "pass"`（规范本身健全，无 blocking finding）
→ 判定表第 1 条不命中 → 第 2 条命中 → `route: "execution"`。

**通过标准**：`compliance.verdict == "fail"`，`validity.verdict == "pass"`，
未达成的判据**逐条列出**，`feedback.to == "cfd-executor"`，指令具体可执行。

> 判据：注入 1 与注入 2 的 `blocking finding` 应指向**不同性质的字段**——
> 注入 1 指向 `physics.*`（物理设定错，规范的问题），
> 注入 2 应**没有** blocking finding（产物没达标，执行的问题）。

### 注入 3：超 Student 限制（应 `escalate`）

把 `02_spec.json` 的 `case.mesh_cells` 改成一个超过 Student 上限的值。

**期望**：`route: "escalate"`，理由是根因不在 agent 可控范围。

**通过标准**：报告里明确告诉用户"为什么人必须介入"，而不是硬跑然后失败。

## 归因正确性 —— 最容易出错的地方

故障注入 1 和 2 的区别很关键：

| 注入 | 现象 | 应返回 | `blocking finding` 指向 | 错误归因 |
|---|---|---|---|---|
| 1 | 结果"收敛了"但物理错 | `spec` | `physics.*`（如 `physics.viscous.model`）| ~~`execution`~~ |
| 2 | 没收敛 | `execution` | **无 blocking finding** | ~~`spec`~~ |

### 怎么判"归因逻辑有没有起作用"

**不要只看 `route` 相不相同——那会误判。** 判据是 `blocking finding` 的 `field` 指向：

- 归因**在起作用**：注入 1 的 blocking 指向规范字段（`physics.*`），
  注入 2 没有 blocking（`validity.verdict == "pass"`，问题出在交付物）
- 归因**失效**：注入 2 也冒出一个指向**规范字段**的 blocking finding
  ——那说明审查在替执行为开脱

> **为什么不能只看 route**：如果注入 2 做成了"改规范字段"（见上文陷阱），
> 两次注入会都返回 `spec`。那是**注入位置错了**，不是归因坏了——
> 审查者在此处的判断反而是正确的。实测已确认过这一情形。

### 实测基线（2026-09-16，库埃特流算例）

下面三组是**实际跑出来的结果**，用于校准"什么样的注入应得到什么裁决"：

| 注入内容 | 实测 route | validity | compliance | blocking 指向 |
|---|---|---|---|---|
| `viscous.model` → k-epsilon | `spec` ✓ | fail | pass | `physics.viscous.model` |
| 规范 `max_iterations` → 10 | `spec` ⚠️ | fail | fail | `convergence.max_iterations` |
| 规范健全 + 产物只跑 10 步 | `execution` ✓ | pass | fail | 无 |

> ⚠️ **原始产物不在仓库里。** 运行产物整体被 `.gitignore` 排除（`runs/`），
> 所以 clone 之后**看不到这三组运行记录** —— 上表是它们的结论摘要。
> 自己跑一遍注入即可复现，`runs/<你的run-id>/review_N.json` 会有同样的字段。

**第 2 行是反面教材**：它注入到了**规范里**，因此返回 `spec` 是**对的** ——
不是归因失效，是注入位置错了。

**第 3 行才是「注入 2」的正确形态**，它正确返回了 `execution`。

**结论**：判定表的两条规则都在正常工作。构造注入时，先问自己一句
**"这个缺陷该由谁来修？"** —— 该由定规范 agent 修的，注入到规范里；
该由执行 agent 修的，让产物不达标但别碰规范。

调度器还要注意：若连续两轮的 `feedback.instructions` 几乎一样，说明回退没生效，
应当停下来重新判断归因，而不是继续循环烧时间。

## 回归基线（2026-09-17，water-pipe 瞬态算例）

用于衡量**流水线本身的优化是否有效**。改动编排逻辑、文档结构或 agent 定义后，
用同一个算例复跑，对比这张表。

| 指标 | 基线 |
|---|---|
| 总墙钟 | ≈ 78 min |
| 总 tool uses | 570 |
| 总 tokens | 1,120,666 |
| **executor tool uses** | **250** ← 主要优化标的 |
| 回退次数 | spec 1 次 / exec 0 次 |
| 人工关卡次数 | 2 |
| 最终 route | `accept`（13/13 判据达成） |

分阶段：

| 阶段 | agent | 墙钟 | tool uses | tokens |
|---|---|---|---|---|
| S1 勘察 | spec-author | 17.6 min | 67 | 123,683 |
| S2 定规范 | spec-author | 10.5 min | 49 | 165,064 |
| **S4 执行** | **executor** | **26.5 min** | **250** | **299,428** |
| S5 审查① | reviewer | 6.2 min | 47 | 157,393 |
| S2 修订（回退） | spec-author | 4.3 min | 43 | 129,604 |
| S4 后处理（回退） | executor | 9.3 min | 74 | 131,155 |
| S5 复审② | reviewer | 3.5 min | 40 | 114,339 |

**读法**：executor 一个角色吃掉 35.8 min / 324 tool uses（含回退轮），占全程 46%。
而它**绝大部分时间不在算流体，在做 API 考古** —— 这正是后来补
`solver-api-26.1.md` 与 `verify_api_paths.py` 的直接动因
（见 `references/solver-api-26.1.md` 开头）。

审查（reviewer）两轮共 9.7 min，产出 2 个真实缺陷发现。**这个角色不要削** ——
它每一轮的性价比是全程最高的。

### 优化的验收标准

```
executor 的 tool uses 应【显著下降】        ← API 文档生效
回退次数应为 0                              ← 判据良构性检查生效
而 route 仍须是 accept、判据仍须全部达成     ← ★ 若为了提速让审查变松，那是负优化
```

最后一条是重点：**只快不严 = 负优化**。

## 还能拿什么练

不限于库埃特流。按主题选算例，都有各自的检验价值：

| 主题 | 适合练什么 |
|---|---|
| 基础流动 | 库埃特流、自然对流、旋转参考系 |
| 外流 | 翼型、管流 |
| 传热与相变 | 芯片散热、凝固/融化 |
| 多相与反应 | 旋风分离器、反应器 |
| 多孔介质 | 催化、过滤 |
| 瞬态与自由面 | 溃坝、空化、射流 |
| 组分输运 | 甲醛泄漏、燃烧 |

**本项目不附带这些网格** —— 自行准备。

**选算例的原则：优先挑有解析解或成熟经验关联式的。** 因为流水线的核心价值是
**独立审查**，而审查者的物理核验能力只有在"有正确答数可对"时才检验得出来。

- **库埃特流** —— 速度剖面严格线性、壁面剪应力有闭式解（见上）
- **自然对流** —— 有成熟的 Nu 数经验关联式可对照，同样能逼出审查者的核验能力
- **泊肃叶流 / 平板绕流** —— 同类，都有经典解

反之，一个只有"残差收敛了"可判的算例，**检验不出审查环节是否真的在工作**。
